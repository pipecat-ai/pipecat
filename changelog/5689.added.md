- Added `LLMWithBackend` (`pipecat.pipeline.llm_with_backend`), in alpha: its API is likely to change between releases. It makes any LLM service, text or speech-to-speech, the conversational frontend of a bot with a backend, with a `BackendLLMWorker` as the backend that does the work it hands off: the split `OpenAILiveLLMService` uses for client delegation, for any frontend. The service drops into a pipeline's LLM slot, installs its tools on the frontend as built-in tools (never part of the context's tool set), registers a local backend worker itself, and attaches to the backend for the pipeline's life; a backend given by name may run in another process on a shared bus. The two exchange messages: the `delegate` tool puts a message to the backend and returns at once, so the frontend acknowledges while the backend works, and everything the backend writes comes back as a message in the frontend's conversation marked `Backend:`, which runs the frontend when the output asks to be spoken. A second request joins the work in progress, a correction changes it, and the `cancel_delegated_work` tool stops it: the backend's pipeline is interrupted, every function call in flight is cancelled, and the cancellation is noted in its conversation. A `BackendConnector` sets how a request is worded from a `BackendRequestStrategy` (`TranscriptBackendRequestStrategy`: the conversation since the previous delegation, the default for a text frontend; `ExplicitBackendRequestStrategy`: a request the model words itself, the default for a speech-to-speech frontend), whether the frontend runs on the immediate `delegate` result (`respond_on_delegate`), whether every exchange with the backend is sent to the client as an RTVI server message for debugging (`client_trace`), and how each output is rendered into the conversation (`render_output()`, which gives a spoken output a note asking the frontend to relay it on whatever turn it lands on); the backend's own function calls are recorded there too, silently, as `Backend (working): name(args)`, so the frontend can say what the backend is doing if asked, and reported to clients over RTVI. `BackendLLMWorker` gains the `attach`, `message` and `cancel` jobs that carry this, which `OpenAILiveLLMService`'s client delegation drives too; a built-in `report_result` tool its model calls to tell the user something while it goes on working, since what the model writes beside tool calls is notes on the work and is not spoken; and `send_output()`, which sends one output of the app's own to the frontend on the same channel as the model's, as given unless `apply_transform_output=True`. `OpenAILiveLLMService` declines both roles, since it is a frontend with a backend of its own, and `InworldRealtimeLLMService` and `UltravoxRealtimeLLMService` decline the frontend role, since neither can hear a backend. See `examples/multi-worker/llm-with-backend/`, one engineering assistant with three frontends, and the evals in `evals/llm-with-backend/`.
