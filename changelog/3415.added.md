- Added support for clients sending files and images to the bot via the new RTVI `send-file` message, incorporating them into the LLM context.
  - New frames: `FileRawFrame`, `InputFileRawFrame`, and `UserFileRawFrame`, carrying a file payload as inline base64 bytes or as a URL.
  - New `LLMContext` methods: `create_file_message()`, `create_file_url_message()`, and `add_file_frame_message()`, producing universal `file_base64` (base64 data URL) and `file_url` content items translated per adapter (Anthropic, AWS Bedrock, Gemini, OpenAI Chat, OpenAI Responses). Unsupported MIME types raise during conversion rather than being silently dropped, so the invalid message can be cleaned up automatically (see below). AWS Bedrock document names are sanitized to satisfy Bedrock's character restrictions.
  - File URLs are resolved at the LLM service, right before each completion, because the right resolution depends on the provider: each adapter declares which URLs its provider can consume directly (public `http(s)` per supported MIME type, `s3://` via Bedrock's IAM, `gs://` via Vertex Gemini's IAM, Files API URIs for Gemini), and those are passed through for the provider to fetch itself. Any other URL is downloaded by the service's new `FileResolver` (`pipecat.utils.file_resolver`) and inlined at conversion time — the context itself stays canonical, holding only the URL, while the downloaded bytes live in the resolver's in-memory cache, keyed by URL. Each file is fetched and decoded once, not per turn, and services sharing one resolver instance (e.g. services switched between mid-session) reuse each other's downloads while still making their own per-provider pass-through decisions. A URL is assumed to identify immutable content (uploads mint a fresh URL each time); `FileResolver.forget(url)` forces a re-fetch when an application knows a URL's content changed.
  - `FileResolver` is configured per LLM service via the new `file_resolver` parameter. It downloads `http(s)` URLs only when the resolved address is publicly routable or falls within its `allowed_url_networks` CIDR ranges (defaulting to the `PIPECAT_ALLOWED_FILE_URL_NETWORKS` env var; SSRF guard; redirects refused, 50 MB cap), and delegates any other scheme to its `FileStorage`. Subclass it to fetch from credentialed backends.
  - New `FileStorage` interface (`pipecat.utils.file_storage`) with a `LocalFileStorage` default implementation. `save()` returns a URL the backend can later resolve (`pipecat:<id>` for local storage); a custom backend can mint e.g. `gs://` or `s3://` URLs, which the LLM provider may then fetch itself without the bot in the loop. A backend whose URLs are all uploads it owns can set `delete_after_load` (as `LocalFileStorage` does) to have a file removed once its bytes are cached by the resolver, which then serves every later use of the file; it stays off for backends whose URLs may point at shared data.
  - The development runner gains a session-scoped `POST /sessions/{session_id}/files` upload endpoint (50 MB cap), mirroring Pipecat Cloud's session routes; it's enabled with the new `-u/--uploads-folder` flag (or `PIPECAT_UPLOADS_FOLDER` env var) and responds with an RTVI file source (`{"type": "url", "url": "pipecat:<id>"}`) the client passes straight back in `send-file`. A session's uploads are deleted when its bot session ends; `--uploads-folder-max-files` (default 10) trims the oldest uploads as a backstop. A flat `POST /files` also exists for transports whose clients never learn a session id (no session-end cleanup there). `/start` responses advertise the route to use as `fileUploadUrl` (relative to the `/start` endpoint's origin; omitted when uploads are disabled), so clients never reconstruct upload routes themselves. To back the endpoints with a custom `FileStorage` (e.g. a cloud bucket) instead of the local uploads folder, define a `create_file_storage()` function alongside your `bot()`: whichever host runs the bot discovers and calls it the same way, so the bot code stays identical across hosts. The active backend is injected into the bot as `runner_args.file_storage` — hand it to your LLM service's `FileResolver` so send-file messages can resolve the URLs it mints.
  - `LLMContext.remove_invalid_file_message()` removes the oldest file or image message added since the model's last successful reply when the OpenAI, Anthropic, AWS Bedrock, or Gemini LLM service determines a request was rejected (including a local resolution or conversion failure that never reached the API), preventing the context from getting permanently stuck.
