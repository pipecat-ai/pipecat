- Deprecated `ErrorFrame.fatal`, the `fatal` argument of `FrameProcessor.push_error()`, and `FatalErrorFrame`, all of which will be removed in 2.0.0. A fatal error cancelled the pipeline outright, taking a decision that now belongs to the application. Passing `fatal=True` still cancels and now emits a `DeprecationWarning`. There are two replacements, depending on what the error means:

  - The error left the processor reporting it unable to do any more work: report it with `push_error(..., treat_as_permanent=True)`. The processor is marked unusable — services stop accepting work and stop reconnecting — and the `PipelineWorker` applies its `processor_unusable_policy`: report the error and keep running, so the application can fail over to another provider (`CONTINUE`, the default), end the pipeline once queued frames drain (`END`), or cancel it immediately (`CANCEL`, which matches what `fatal=True` did). The flag is only needed for a failure the error's category doesn't already convey, since a permanent category costs a processor its usability on its own.

  - The error isn't about any processor's state, and the pipeline should stop anyway: push the `ErrorFrame` without `fatal` and follow it with an `EndWorkerFrame`, which ends the pipeline after queued frames drain. Use `CancelWorkerFrame` instead to abandon them, as `fatal=True` did.
